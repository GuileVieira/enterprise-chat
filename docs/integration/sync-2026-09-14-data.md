# Auditoria estática de compatibilidade de dados/startup

Base comparada: produção `3e479c7c7` versus árvore mesclada em 2026-09-14. Nenhum banco, startup ou migração foi executado.

## Conclusão operacional

Não recomendo apontar a primeira inicialização diretamente para o único banco de produção sem snapshot. Há mutações automáticas de metadados/referências e um novo processo de exclusão por retenção. Faça snapshot consistente de MongoDB e backup dos arquivos no storage/volumes; um snapshot só do Mongo não recupera objetos apagados pelo sweep. No ensaio, use uma cópia isolada do storage e integrações externas desativadas, nunca os buckets de produção. Se Meilisearch for operacionalmente importante, preserve também seu volume ou aceite reconstruí-lo. O ensaio mais seguro é restaurar o snapshot em um clone, iniciar com os mesmos env/config e comparar contagens e amostras antes/depois.

## Mutações automáticas relevantes

1. **Reconciliação de arquivos de Projects (já existia no HEAD, continua ativa).** `api/server/index.js:500-505` chama `checkMigrations` após abrir a porta. `api/server/services/start/migration.js:12-113` percorre todo Project com tenant. Para cada `fileIds`, resolve `file_id` ou `temp_file_id`, troca `File.projectId` para o projeto que declarou a referência (`66-76`), preenche `tenantId` ausente (`70-75`, `88-92`), normaliza IDs temporários e regrava `Project.fileIds`, removendo referências sem arquivo (`46-63`, `96-104`). Também garante ACL de tenant (`36-43`). Não apaga documentos File/Project, mas pode remover referências e reatribuir arquivo se dados atuais estiverem inconsistentes. Como o arquivo é idempotente mas não tem dry-run no startup, exige snapshot/ensaio.

2. **Traffic Diary/Meta Ads (já existia no HEAD).** `api/server/services/start/migration.js:115-158` converte todo registro sem `kind` para `kind='manager'` (`121-124`), remove índices antigos/não únicos e cria unique `{projectId,userId,kind,date}` (`130-152`). Isso reinterpreta entradas antigas como diário do gestor. Se houver duplicatas nessa nova chave, `createIndex` falha e o erro é logado; documentos não são apagados. O schema confirma a cardinalidade nova em `packages/data-schemas/src/schema/trafficDiary.ts:32-60`.

3. **Retenção de arquivos (novo no merge).** `api/server/index.js:255-260` inicia `startExpiredFileSweep`. `packages/api/src/files/sweep.ts:268-369` busca arquivos cujo `expiredAt` venceu, chama a exclusão do storage e remove/resolve o registro pelo fluxo normal; falhas são mantidas e reagendadas. Executa imediatamente e depois em intervalo (`397-429`), salvo `FILE_RETENTION_SWEEP_INTERVAL_MS=0` (`401-405`). Arquivos legados sem `expiredAt` não entram no sweep, mas qualquer registro atual já contendo uma data vencida será elegível na primeira inicialização.

4. **Preview órfão (já existia no HEAD).** `api/server/index.js:225-233` dispara sweep; `packages/data-schemas/src/methods/file.ts:1211-1223` muda `status: pending` com mais de 5 minutos para `failed` e `previewError: orphaned`. Não apaga arquivo, mas muda estado visível.

5. **Roles/capabilities (startup mutável, merge amplia defaults).** `api/models/index.js:11-17` roda `initializeRoles`, roles ACL e grants. `packages/data-schemas/src/methods/role.ts:87-155` renomeia `SHARED_GLOBAL` para `SHARE`, remove a chave antiga e preenche somente blocos/campos ausentes; valores existentes não nulos são preservados. `packages/data-schemas/src/methods/systemGrant.ts:508-542` faz upsert dos grants ADMIN ausentes. É alteração persistente, porém aditiva salvo a migração nominal de permissão.

6. **Code environments (novo, coleção nova).** `api/server/index.js:196-202` inicia reconciliador. `packages/api/src/code/lifecycle.ts:95-138`, `139-228`, `230-240`, `343-357` pode apagar CodeEnvironment e ACL associados quando há remoção já iniciada/commitada, registro incompleto antigo ou dono inexistente. Não alcança Projects, meetings, users ou conversas legadas; é relevante se esta árvore já foi executada parcialmente e criou registros de code environment.

## Índices e busca

- `MONGO_AUTO_INDEX` continua controlando criação automática (`api/db/connect.js:24,57`). Se não for `false`, Mongoose tentará criar os muitos índices novos do schema de conversa (`packages/data-schemas/src/schema/convo.ts:397-430`). A única unique nova destacada ali é sparse em `agentEventBinding.bindingId` (`425-428`); duplicatas preexistentes desse campo novo são improváveis, mas uma execução parcial pode bloquear o build do índice. Criação de índice não remove documentos.
- A migração ampla de índices tenant é **manual**, não startup: scripts em `package.json:141-142`; `config/migrate-tenant-indexes.js:1-19` desliga auto-index/create e chama a rotina. Ela cria constraints tenant, depois derruba índices unique globais. Não deve ser executada implicitamente junto ao deploy; deve ter dry-run, writers parados e snapshot.
- `api/db/indexSync.js` roda em background no startup (`api/server/index.js:196-202`). Alterações do merge reconciliam pendências e podem excluir documentos **somente do Meilisearch**, não do Mongo. A lógica já removia hits sem `user`; mudanças novas também limpam itens excluídos da busca. Perda do índice é recuperável por resync, embora afete busca durante reconstrução.

## Compatibilidade dos dados pedidos

- **Orqest Projects:** schema materialmente igual; mudança é apenas tipagem (`packages/data-schemas/src/schema/project.ts:324-390`). `projectId`, memories, snippets, fileIds, Meta Ads e tenantId continuam. Métodos Project tiveram tipagem, sem nova migração destrutiva. O risco vem da reconciliação automática de `fileIds` descrita acima.
- **Meetings:** schema materialmente igual; só anotação TS mudou. `projectId`, `tenantId`, transcript, participantes e insights permanecem (`packages/data-schemas/src/schema/meeting.ts:42-83`).
- **Meta Ads:** payload embutido em Project permanece. Traffic Diary antigo ganha `kind=manager`; essa é a reinterpretação concreta.
- **Users:** campos novos são opcionais/default (`termsAcceptedAt`, fences, preferência de ambiente) em `packages/data-schemas/src/schema/user.ts:131-167`; documentos antigos não são regravados automaticamente por defaults. O TTL `expiresAt` já existia no HEAD.
- **Conversas:** `projectId` permanece intacto e indexado (`packages/data-schemas/src/schema/convo.ts:371-382`). `chatProjectId` é campo separado (`363-367`) e o código de save impede que updates genéricos o alterem (`packages/data-schemas/src/methods/conversation.ts:2127-2128`), portanto não converte Orqest `projectId`. A coleção ChatProject é separada (`chatprojects`, `packages/data-schemas/src/models/chatProject.ts:6-12`). Campos novos de pin/archive/event actor são opcionais; não há backfill global.
- **Retenção de conversas:** o TTL em `expiredAt` já existia, mas o merge amplia atribuição de expiração no save. Com `retentionMode=ALL`, um save pode definir `expiredAt` (`packages/data-schemas/src/methods/conversation.ts:2134-2168`), e o TTL Mongo depois apaga a conversa. Sem essa configuração, conversas normais explicitamente não temporárias continuam limpando `expiredAt` (`2170-2180`). Validar a configuração efetiva antes do deploy é obrigatório se histórico precisa ser permanente.

## Checklist verificável antes do primeiro startup

- Snapshot/restore testado de MongoDB; clone preferível para ensaio.
- Inventário no clone de Projects com `fileIds` mortos, temporários ou arquivos referidos por mais de um projeto; comparar antes/depois.
- Contagem/duplicatas de Traffic Diary pela chave `{projectId,userId,kind/date}`, especialmente rows sem `kind`.
- Inventário de `files.expiredAt <= now`, previews `pending` antigos e configuração `FILE_RETENTION_SWEEP_INTERVAL_MS`.
- Confirmar `interface.retentionMode`/`generalChatRetention` efetivos e `MONGO_AUTO_INDEX`.
- Rodar `npm run migrate:tenant-indexes:dry-run` apenas no clone; a versão sem dry-run requer janela sem writers.
